## Model Statement

This project uses Meta Llama through Ollama on the developer’s local
Windows machine.

Demonstration inputs are synthetic. In Ollama mode, assessments are
generated by the running model. Mock mode uses predefined results and
is labeled separately.

- Exact model tag tested: `llama3.2:3b`
- Runtime: Ollama
- Environment: Developer’s local Windows PC
- Live inference: Successfully run and manually confirmed by the developer.
- Hosted Meta Model API: Not used.
- Non-Meta runtime model calls: None.

Successful inference confirms that the local model integration runs.
It does not establish fraud-detection accuracy, reliable Roman Urdu
understanding, or production readiness.

## Added Since the First Version

### Deterministic Verification-Code Safety Rule

A plain-code heuristic raises detected explicit login/verification-code
requests to high concern when the model assigns a lower concern band.

- The adjustment is disclosed in the UI and incident report.
- The rule was unit-tested using 27 labeled synthetic messages.
- It is a heuristic and can produce both false positives and false negatives.
- It does not prove that a message is fraudulent.
- It does not guarantee that every wording of a code request will be detected.

The 27 synthetic rule tests are not a live-model accuracy evaluation.

## What Is Synthetic

All four demonstration inputs are fictional:

1. Family emergency impersonation.
2. Verification-code request.
3. Legitimate-looking request.
4. Ambiguous urgent message.

They contain no real people, phone numbers, payment accounts, or CNICs.

They are labeled:

“Synthetic example — not a real incident.”

Selecting an example in Ollama mode loads the input only. The assessment
is generated by the running model.

## What Is Mocked

- `AI_PROVIDER=mock` returns predefined assessments for the four
  synthetic examples in English and Roman Urdu.
- These results are labeled “Predefined sample assessment.”
- They are not model-generated output and must not be presented as
  live inference.
- Unit tests mock the Ollama HTTP layer.
- Frontend tests use a stubbed backend.

The application does not silently switch from failed live inference
to a mock assessment.

## Family Verification

Family Verification is a manual independent-checking workflow.

It guides users to contact a person through a previously known number
or another trusted channel and record what they personally confirmed.

- Rasta does not independently verify identity.
- It does not collect or store family code words.
- It does not treat a familiar voice, message delivery, or completed
  checklist as proof.
- User-recorded verification does not automatically clear the assessment.

## Privacy and Deployment Limitations

- The prototype is configured for local, single-user operation.
- Ollama and backend services should remain on loopback.
- Cases are stored in backend memory and disappear on restart.
- The original raw message is not persisted.
- Derived fields and quoted evidence may still contain sensitive content.
- Redaction is best effort, not guaranteed.
- Case endpoints do not currently implement authentication.
- The backend and Ollama must not be exposed directly to the internet.

Public deployment requires additional authentication, authorization,
privacy, and infrastructure review.
